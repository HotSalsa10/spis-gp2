PHASE 2 -- Data Pipeline & Feature Engineering
========================================================================

WHAT WAS DONE
  Built an automated pipeline that takes raw daily sales from the
  database, fills date gaps, engineers 35 time-series features, and
  splits the data into train/test sets for the ML model.

PIPELINE STEPS
  1. Extract daily sales (16,848 rows = 8 ATC codes x 2,106 days)
  2. Validate (check nulls, negatives, duplicates)
  3. Fill missing dates with quantity=0
  4. Engineer 35 features (see below)
  5. Split into train (before 2019) and test (2019 onwards)

OUTPUT FILES (data/processed/ -- git-ignored)
  train.csv          -- 14,544 rows (Jan 2014 - Dec 2018)
  test.csv           -- 2,248 rows (Jan 2019 - Oct 2019)
  features_daily.csv -- 16,848 rows (full dataset with features)

  To recreate:
    python scripts/run_pipeline.py

THE 35 ENGINEERED FEATURES
  All derived from the sales data itself -- nothing external except
  the Turkey holiday and school calendars.

  Calendar (12):
    day_of_week        -- Monday=0 through Sunday=6
    day_of_month       -- 1st through 31st
    month              -- January=1 through December=12
    year               -- 2014 through 2019
    week_of_year       -- Week 1 through 52
    is_weekend         -- 1 if Saturday/Sunday, else 0
    is_holiday         -- 1 if Turkish public holiday, else 0
    season             -- 1=Winter, 2=Spring, 3=Summer, 4=Fall
    is_payday_window   -- 1 if day 1-3 or 15-17 of the month
    is_school_holiday  -- 1 if during Turkish school break
    quarter            -- 1 through 4
    days_to_month_end  -- Days remaining until end of month

  Lags (7) -- "What were the sales X days ago?"
    lag_1              -- Yesterday's sales
    lag_2              -- 2 days ago
    lag_3              -- 3 days ago
    lag_7              -- Same day last week
    lag_14             -- Two weeks ago
    lag_28             -- Four weeks ago
    lag_365            -- Same day last year

  Rolling windows (12) -- Averages/stats over recent days:
    rolling_mean_7     -- Average sales over last 7 days
    rolling_std_7      -- How much sales varied in last 7 days
    rolling_mean_14    -- Average over last 14 days
    rolling_mean_28    -- Average over last 28 days
    rolling_std_28     -- Variance over last 28 days
    rolling_min_7      -- Lowest day in last week
    rolling_max_7      -- Highest day in last week
    rolling_mean_90    -- Average over last 3 months
    rolling_mean_365   -- Average over last year
    ema_7              -- Exponential moving average (7-day)
    ema_14             -- Exponential moving average (14-day)
    ema_28             -- Exponential moving average (28-day)

  Derived (4):
    lag_ratio_7        -- Yesterday's sales / 7-day average
                          (detects demand spikes)
    trend_counter      -- Days since dataset start
                          (captures long-term growth/decline)
    rolling_range_7    -- rolling_max_7 - rolling_min_7
                          (measures recent demand volatility)
    ema_ratio          -- ema_7 / ema_28
                          (captures short vs long-term trend direction)

PHASE 3 -- XGBoost Forecasting Model
========================================================================

WHAT WAS DONE
  Trained an XGBoost machine learning model that predicts daily drug
  sales. Compared it against two simple baselines to prove it actually
  adds value.

HOW IT WORKS
  Input:  36 features (the 35 above + drug category encoded as number)
  Output: Predicted sales quantity for that drug on that day

  The model learns patterns like:
  - "Sales of painkillers go up on weekdays"
  - "If last week's average was high, this week will probably be high too"
  - "Sales dip on Turkish holidays and school breaks"
  - "Demand spikes around payday (1st and 15th of each month)"

TRAINING PROCESS
  1. Load train/test CSVs from Phase 2
  2. Encode drug categories as integers (M01AB=0, M01AE=1, etc.)
  3. Drop first-year rows where lag_365 has no data
  4. Try 512 hyperparameter combinations using GridSearchCV with
     TimeSeriesSplit (5 folds) to find the best settings
  5. Evaluate on the held-out 2019 test data

RESULTS
  Model               MAE       RMSE      MAPE(%)
  --------------------------------------------------
  Naive (lag_1)       4.23      7.23      98.42
  Moving Avg (7d)     2.89      4.98      67.83
  XGBoost             1.06      2.29      20.56

  MAE  = Average prediction error (lower is better)
  RMSE = Like MAE but penalises big misses more
  MAPE = Average error as a percentage

  XGBoost achieves MAE 1.06, beating the 7-day moving average by 63%.

TOP FEATURES (what the model relies on most)
  ema_14            0.48   (14-day exponential moving average)
  ema_7             0.27   (7-day exponential moving average)
  rolling_mean_14   0.03   (14-day rolling average)

BEST HYPERPARAMETERS
  n_estimators:      800
  max_depth:         6
  learning_rate:     0.03
  subsample:         0.8
  colsample_bytree:  0.8
  min_child_weight:  1
  reg_alpha:         0

SAVED ARTIFACTS (models/ -- git-ignored)
  xgboost_forecaster.joblib  -- The trained model
  label_encoder.joblib       -- Drug category name-to-number mapping
  metrics.json               -- Results table in JSON

PHASE 4 -- Risk Classification & Order Recommendations
========================================================================

WHAT WAS DONE
  Added a risk classification layer on top of the forecaster.
  For each drug category the system answers:
    1. What is the current risk tier?
    2. How many units should we order to cover the next 30 days?

RISK TIERS (Days of Stock = current_stock / daily_demand)
  CRITICAL  : DoS < 3 days  -- likely stockout within 3 days
  LOW       : 3 to 7 days
  OK        : 7 to 30 days
  OVERSTOCK : 30+ days

ORDER QUANTITY FORMULA
  safety_buffer = daily_demand * safety_days  (default safety_days = 3)
  order_qty     = max(0, forecast_30d + safety_buffer - current_stock)

RESULT OBJECT (RiskAssessment -- immutable dataclass)
  atc_code      : Drug category code
  current_stock : Units on hand
  forecast_30d  : Predicted demand over next 30 days
  daily_demand  : forecast_30d / 30
  days_of_stock : current_stock / daily_demand (null if demand = 0)
  risk_tier     : CRITICAL | LOW | OK | OVERSTOCK
  order_qty     : Recommended units to order

KEY FILES
  spis/models/risk_classifier.py  -- All risk logic
  scripts/assess_risk.py          -- CLI entry point

PHASE 5 -- Flask REST API
========================================================================

WHAT WAS DONE
  Exposed the forecasting and risk classification logic as HTTP
  endpoints. External systems (or the Streamlit dashboard in Phase 6)
  can now query SPIS over a standard REST API.

ENDPOINTS
  GET /health
    Returns {"status": "ok", "version": "0.1.0"}
    Always HTTP 200 if the server is running.

  GET /api/v1/risk
    Runs a full risk assessment for all 8 ATC codes.
    Returns:
      assessed_at  : ISO-8601 UTC timestamp
      safety_days  : Safety buffer used in order-qty calculation
      results      : List of per-ATC-code risk records (see Phase 4)
    HTTP 503 if model artifacts are not loaded.

  GET /api/v1/forecast/<atc_code>
    Returns a 30-day demand forecast for a single ATC code.
    Example: GET /api/v1/forecast/M01AB
    Returns:
      atc_code       : The code requested
      forecast_30d   : Total predicted demand over 30 days
      daily_demand   : forecast_30d / 30
      forecast_start : First date of the forecast window (ISO date)
    HTTP 404 if the ATC code is unknown.
    HTTP 503 if model artifacts are not loaded.

APP DESIGN
  - Flask app factory pattern: create_app(config=None)
  - Model artifacts loaded once at startup (eager loading)
  - If artifacts are missing, server starts but returns 503 on ML routes
  - Routes registered via Blueprint for clean separation

TO START THE SERVER
  python scripts/run_api.py
  python scripts/run_api.py --host 0.0.0.0 --port 8080 --debug

  Requires model artifacts. Run these first if needed:
    python scripts/ingest_kaggle.py
    python scripts/run_pipeline.py
    python scripts/train_model.py

KEY FILES
  spis/api/app.py      -- Flask app factory (create_app)
  spis/api/routes.py   -- All route handlers (Blueprint)
  scripts/run_api.py   -- CLI server launcher

========================================================================

WHAT WAS DONE
  Built a single-page Streamlit dashboard that shows inventory risk
  tiers, 30-day demand forecasts, and recommended order quantities for
  all 8 ATC codes. Imports model artifacts directly (no running API
  required).

FILES
  spis/dashboard/app.py   -- Main Streamlit app (~100 lines)
  scripts/run_dashboard.py -- Convenience launcher

HOW TO RUN
  # Activate the virtual environment first, then:
  python scripts/run_dashboard.py
  # Opens at http://localhost:8501

  # Optional: custom port
  python scripts/run_dashboard.py --port 8502

  # Or directly via Streamlit:
  streamlit run spis/dashboard/app.py

WHAT IT SHOWS
  1. Summary row: four metric cards (CRITICAL / LOW / OK / OVERSTOCK counts)
  2. Risk table: all 8 ATC codes with stock, 30d forecast, daily demand,
     days-of-stock, risk tier (colour-coded rows), and order quantity
  3. Bar chart: recommended order quantities per ATC code
  4. Medications table: all 57 individual drugs with name, ATC code, unit,
     risk tier and order quantity (inherited from parent ATC group)

DESIGN DECISIONS
  - Imports directly from spis.models (not the Flask API) for simplicity.
  - Uses @st.cache_resource for model/encoder (loaded once per process).
  - Uses @st.cache_data(ttl=300) for assessment results (refreshed every 5 min).
  - Guard at startup: shows clear error if pipeline/model artifacts are missing.
